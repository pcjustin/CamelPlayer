# Changelog

## 0.4.2

Upgrading from 0.4.1: the library gains two indexes (library schema 22), and a copy of the library as it was is kept beside it as `library.db.v21.bak`. 0.4.1 refuses the newer library, so to go back to it, close CamelPlayer and, in `%LOCALAPPDATA%\CamelPlayer`, replace `library.db` with that copy. The settings keep their schema.

As with every new version, the first complete library scan reads every MP3, and every file an earlier version could not read, once more.

Changed since 0.4.1:

- **A library or settings file another program holds is left as it is:** any error opening `library.db`, such as an antivirus or backup program holding it for a moment or a full disk, was taken for damage: the library was put aside as `library.db.bad`, its last changes deleted, and a backup or an empty library put in its place. A `settings.json` that could not be opened gave the defaults and the first-run guide, and the next change saved them over your settings. Only real damage is repaired now; otherwise CamelPlayer says another program may be using the file, that nothing was changed, and offers Try again and Close.
- **Two dialogs at once no longer close CamelPlayer:** a dialog that opened while another was showing ended the program, so a new installation that also found an installed update closed two seconds after starting, and the restart question after an update download or a scan's offline notice could do the same. A second dialog now waits for the first to close. Opening the first-run guide from Settings with a network player or AirPlay receiver as the output also closed CamelPlayer; the guide now lists every kind of output.
- **Other crashes:** an error in playback's own work between commands, such as moving to the next track or buffering a slow file, ended the program, and now ends that playback with the error shown. Kernel Streaming could let the driver write into freed memory when a start or resume failed. After Reset everything, the next start, and opening Settings, closed CamelPlayer when an entry in the data folder could not be read. A crash in some places left the dead program waiting for ever, so starting CamelPlayer again did nothing until it was ended in Task Manager; it now ends within 20 seconds.
- **Closing is clean and quick:** a network player's own pause, play or seek arriving as CamelPlayer closed ended it with a crash report behind a normal exit, and the library's background work could be freed while the window still read it. The search index could hold closing for good, and Discord starting or stuck, or a stuck download of cloudflared, for seconds at a time. Each now stops at once.
- **Editing the EQ no longer takes ever more memory:** every change kept the editor's old rows, and the output switches in Settings likewise: adding and removing a band 150 times took CamelPlayer from 305 MB to 2.2 GB. The old rows are now freed.
- **A file a tagger rewrites keeps its history:** a tagger that writes a file anew and puts it in place of the old one left a file the scan took for another, so its plays, favorite and rating were lost, and its playlist entries went unavailable and were deleted after 30 days. The new file at that path now takes over the old one's record.
- **An action never reaches tracks you did not select:** a scan that changed the library while rows were selected moved other tracks into their places, and Add to favorites, Reset play statistics, which cannot be undone, and the queue and playlist actions reached those. When the library has changed since you selected, nothing is done now, and a notice asks you to select again.
- **A share that blinks keeps its files' history:** when a folder a change notification named could not be looked at, for any reason, its files were marked missing, and on a share they came back as new tracks without their plays and playlist entries. Only a folder that is gone loses its files now; any other failure keeps them and scans the library folder again.
- **One unreadable file no longer holds up the library:** a file held by another program, denied to your account or refused by the tag reader left every scan incomplete, so deleted files were not marked missing, moves were not matched and albums were not rebuilt for as long as it stayed. Such a file now keeps its record as it was and is read again by the next scan.
- **The queue and the settings survive a full disk or a power cut:** a queue save that failed was taken for done, so a restart could start another track at another place; a power cut right after a settings save could leave `settings.json` empty and the session's changes lost; and an EQ band in it whose type was not text made the whole file count as damaged, every setting going back to its default. A failed queue save is now made whole the next time, the settings reach the disk before they replace the old file, and such a band alone is dropped.
- **A FLAC plays to its end:** some rips carry bytes after the last frame, and each track of such an album skipped to the next about ten seconds before its end and was marked failed, so Previous could not go back to it. A FLAC behind two ID3v2 tags, or one with a footer, was refused by the default decoder and not checked against its MD5. Both now play whole.
- **A track removed from the queue is not played:** the next track is prepared well before the current one ends, and removing it, clearing the queue or adding tracks in place of autoplay's left it ready, so a track just removed still played whole. It now goes with its entry, and the next track in the queue plays.
- **A seek while a slow file buffers:** a seek, a settings change or a change of the Windows default device while a file from a slow share was buffering left it paused for good, as a DSD256 track over Wi-Fi stopped at 1:01. It now buffers again and plays; a track you paused stays paused.
- **A pause on WASAPI no longer skips:** a pause threw away what the device still held, 10 to 200 ms by the mode, so every pause skipped that much of the track. It now plays first when playback resumes.
- **AAC and ALAC in MP4 files:** a fragmented M4A played nothing and was listed as 0:00 long; one whose timescale is not its sample rate showed a length of 0 and seeked to the wrong place; and seeking back near the end of an AAC or ALAC track stopped playback with a decode error. They now play and seek as other files do.
- **DTS-CD plays as the disc does:** a DTS-CD whose frames declare a 20-bit or 24-bit source played 16 or 256 times too loud, clipping hard, and the encoder's dynamic-range control was applied, unlike the disc's own mix. The downmix to stereo guessed each channel's speaker from the channel count, so the LFE of a stereo track went into both sides, and a mono track with an LFE played the LFE on the right. Every DTS-CD now decodes at the reference decoder's level, uncompressed, and is downmixed by each channel's own speaker.
- **DTS-CD rips that start with silence, and damaged DTS frames:** a rip with a second or more of digital silence before its first frame was taken for PCM and played as loud noise; up to a minute of silence is now passed over first. Frames with two subframes and an LFE, raw frames of odd length, and damaged frames that brought a made-up channel or extra samples stopped a track or spoiled the frames after them, and a long silent stretch took hundreds of megabytes; each is now decoded as the reference decoder does, or passed over.
- **Crossfades keep their length:** the fade out of a track with a higher sample rate or more channels than the device was cut short without a word: a 10 s fade from a 192 kHz track on a 96 kHz device lasted under 6 s. DSD converted to PCM could also have its resampler emptied in the middle of a track before a crossfade, spoiling the fade.
- **DSP changes and tails:** a second change within a fade, as dragging an EQ band makes, jumped from the blend to the new setting alone, and now fades from what is heard. Turning DSP off while a convolution's tail played after the last track failed playback; a track added after the end had its tail cut short or left out; and DSD sent as it is could get PCM bytes at its end. Each end now plays its own whole tail, and DSD none.
- **EQ presets are read as written and kept in range:** "Gain +3.0 dB" was imported as 0 dB without a word, and "nan", "inf" or values beyond the ranges went straight into the EQ, so a preset sounded different after a restart and one extreme band made the output silent. An import now reads a plus sign, holds gain, Q and frequency to the ranges the settings keep, leaves out what is not a number and names the lines it changed; the playback engine leaves out any band beyond those ranges.
- **An impulse response too long is refused at once:** one longer than convolution takes was decoded whole before being refused, and again every time the DSP chain was set up, so a long recording chosen by mistake took several times its size in memory and a large one failed playback. Its length is now checked first, once. A .zip, or a damaged download, that claims a file far larger than it holds no longer stalls CamelPlayer.
- **Conversions:** a 16-bit track resampled for a 24-bit DAC was dithered at the 16-bit level, about 48 dB more noise than needed, and is now quantized at the device's depth. With DSP, ReplayGain, software volume or crossfade on, every change to a conversion setting reopened the device and broke the sound, though nothing it plays changed; it now reopens only when the path changes.
- **Devices:** WASAPI shared mode refused every track on a headset or USB device that mixes below 44.1 kHz, and now resamples to it when conversion is allowed. With no ASIO driver saved, the first registered one was loaded even when its device was gone; the first available one is loaded now. Opening the control panel of an ASIO driver that could not load stopped playback as if the track had failed; it now only says why.
- **Autoplay stops after three tracks fail:** with no track the device could play, as with conversion off, autoplay went through the library one track after another, each failing at once, filling the queue. It now stops once three tracks in a row have failed, and the last one's error stays shown.
- **Smaller playback fixes:** a track played, stopped and played again within half a second did not play; after a manual change near a track's end the length shown could be that of a track never heard; a DTS-CD or ADPCM WAV restored at start showed no format until played; DSD of the 48 kHz family showed as DSD69; and a WAV or AIFF whose share goes away now says it can no longer be read.
- **ReplayGain and waveforms reach the whole library:** every DSD track counted as waiting for analysis and failed again in each session, and with 200 or more of them the rest of the library was never analyzed. Files that failed while a share slept held up the analysis until a restart, and a file interrupted by playback was recorded without a value. DSD is left out as meant, failed files and offline folders no longer block the rest, and an interrupted file is measured again.
- **Sort order after a change between stroke order and Bopomofo:** switched back before the rebuild had finished, rows kept the other order and sorted out of place, and album lists opened meanwhile mixed the two, the jump bar pointing at the wrong albums. Both now end in the order chosen.
- **Library folders a NAS or a mount cannot watch:** on storage that refuses change notifications, as some NAS and SMB servers, rclone and WebDAV mounts do, the whole folder was scanned every minute or every few seconds; it is now left to its regular check. A change in a folder whose scan did not finish waited up to 6 hours, and a change to a file the library does not read, such as desktop.ini at the top of a library folder, rescanned the whole library. A NAS that had dropped showed its name and paths in lowercase.
- **Renamed files and exported playlists:** a renamed or moved file kept its old name in the library, so a playlist exported then named a file that no longer existed, and every folder in an exported playlist came out in lowercase, which fails on a player that reads paths case-sensitively, such as a NAS's own media server. Both are now spelled as on disk.
- **Lists show all their rows:** rows read while a scan changed the library, or whose read failed, stayed blank until scrolled away and back; View all on the Listening page's most played lists stopped at 100 rows rather than 500; a folder of the folder tree opened twice quickly during a scan listed its contents twice; and Go to playing with every folder closed left the page looking empty until the mouse wheel moved it.
- **Search:** searching "aimer" also listed chelly as an artist, from a track credited "Aimer with chelly"; only names that hold the search are listed now. An album or artist chosen among the search suggestions opened with no way back, and Back now returns to where the search was made.
- **Playlist edits in a row:** pressing Delete twice quickly in a playlist refused the second with "the playlist has changed" and undid it; edits are now applied one after another.
- **A network player is followed again, and left alone after a stop:** played to again after it had stopped answering, a player showed position 0, its changes of track went unseen and its own pause and next were not followed until a restart. After a stop, CamelPlayer went on asking a player how it was twice a second, which can keep a streamer from its network standby; it now leaves it until played to again.
- **No more false "in use by another source":** an OpenHome player on its radio or Spotify stopped with that notice at the first play and played only at the second; one that still reported its earlier source for a moment, or finished a very short track before hearing of the next, did the same.
- **Tracks on a network player stay in step:** a next track the queue had dropped was still played, as silence or under the old track's title; a track whose estimated length was short pushed its end into the next track, so every track after played under the title of the one before; a late report of the track just left jumped back a track; and on a resampled stream the track being left showed half its position.
- **Network players that were not found or could not play:** a player whose description holds two devices was not listed; a computer with many network adapters, such as Hyper-V switches or VPNs, found no network player or AirPlay receiver at all; a player that names itself in an encoding other than UTF-8 was not listed; a player with https addresses failed every command; and one that could not tell its formats when chosen, as one waking from standby, refused every track until a restart.
- **Streams and events:** a WAV stream past 4 GB, such as over an hour of 24-bit 192 kHz audio, stopped there on a player that trusts its header, and at once on the Chord Poly, which looks for what follows the data where the header says it ends; a DSD track that ended short ended with a thump; and a player that reports no position counted a pause as played time. Events sent in chunks were dropped, a subscription granted without end was renewed every second, subscriptions were left on a player when a later one was refused, and a search for players whose socket failed took a whole processor core.
- **AirPlay receivers:** a receiver that refused a session, as a HomePod does while only people in the home may play to it, stayed refused after its own setting changed; turning it on now asks it again. A receiver in a group turned off in Settings went on playing with no row to take it out, and now leaves the group. One that joins mid-track, such as an Apple TV, shows the playing track at once, and a click on another track with crossfade on no longer leaves the receivers showing the wrong title.
- **Space works the control the keyboard reached:** a switch, check box, button, drop-down or list row reached with Tab could not be pressed with Space, which played or paused instead; Space on the Autoplay switch started playback. They now take it, and after a click Space still plays or pauses.
- **Changes while an output's settings window is open:** a device plugged in or a network player found meanwhile was lost, and the next change wrote the old outputs back; on a new installation, closing the main window to the notification area with another output's settings open switched playback to that output. Both now reach the settings as they should.
- **Language and theme:** Start with Windows and a network player's Gapless playback showed Windows' own On and Off in Windows' language, and the queue's Remove buttons kept the old language after a change until a restart. An album named with a placeholder such as "Demos {1}" got another value inside its name in Home's summary. Column dividers could not be seen after Settings changed the theme, an album's format badges appeared on another page when Windows switched between light and dark, and on Windows 10 the file details window kept its first background.
- **Covers and pictures:** a click on a heart, a new track or an opened folder blanked covers for a moment; Home's View all walls and the most played albums did not mark the playing album; the player bar now also finds the cover in the album's folder and its first track when the playing file has none. Discord kept the CamelPlayer icon after covers were turned off and on, and with CamelPlayer busy, an artist picture did not show after Allow.
- **Windows:** with the startup entry locked by a policy or a protection program, Start with Windows sprang back without a word, and a note now says so. A file whose path held "--background" opened in the notification area, or not at all. The taskbar button showed a blank icon after Windows was unlocked, and a moved copy left the taskbar group with none; the windows now take the program's own icon.
- **Reset and logs:** Reset interface now also resets the background analysis hours, and Reset playback the scan speed. A CamelPlayer left running for weeks wrote everything into its first day's log, without bound, and hang reports past the number kept; a new log starts at midnight and old ones go.
- **An update with administrator rights checks what it installs:** an update to a protected folder copied the new files from a temp folder that any program of yours can write into, unchecked, and started the new version from them with those rights. Every file is now checked against the list from the verified download before and after it is copied, any difference undoes the update, and the updater loads system DLLs only from Windows' own folder.
- **Updates and repairs leave other files alone:** the release zip has no top folder, so with CamelPlayer unpacked into Downloads, the desktop or a music folder, an update deleted every other file and folder beside it, and a repair first copied all of them to the temp folder, perhaps hundreds of gigabytes. Both now touch only the program's own files.
- **An update cut short is put right:** a sign-out, shutdown or power cut during an update left part of the files, and the next update deleted the one copy of the old version. The updater now keeps a record on disk, and the next update first finishes or undoes the one cut short.
- **Updates no longer fail for nothing:** a new version whose first start took over 30 seconds, as when it migrated a large library with an antivirus reading the new files, was ended and rolled back, and with the old version still closing after 30 seconds, the update gave up and CamelPlayer was gone. A CamelPlayer at a drive's root, or started from a SUBST drive, a short name or a junction, closed for the update and did not come back, or was rolled back while it ran, and a release without notes was not found. Every rollback also kept automatic checks from offering that version again, though a held file or a full disk may have kept it from being installed at all; now only a version that did not start is skipped, and one undone before it started is offered again.
- **The firewall rule's netsh comes from Windows' own folder:** it was started with administrator rights by its bare name, so a netsh.exe left in the current folder could have run instead.
- **Network player addresses are checked as Windows reads them:** a device answering with an address like `http://192.168.1.5:80@example.com/` passed the check that it is on your network, and its description was then fetched from the internet. Such an address is now refused, and this computer's own addresses are accepted only when players are looked for on it.
- **AirPlay resend requests are answered only for the session's speakers:** any device on the network could ask CamelPlayer to send it audio again, up to 65,535 packets at once, holding the stream up for a third of a second.
- **cloudflared gets only its output:** started for Discord covers, it inherited CamelPlayer's network connections, so one CamelPlayer closed to a network player or AirPlay receiver stayed open there.
- **A diagnostic bundle without paths has none:** the impulse response's path, with your user name, was still in its settings, and a folder name holding " via " left the rest of its path in the logs. Local library folders were also listed as network ones.
- **Covers come sooner during a scan:** album thumbnails are now made while a first scan runs, and the scan gives way while the window reads covers: on a NAS over Wi-Fi the slowest covers came about 4 seconds sooner. A cover being shown with every core busy took 14 to 16 seconds and now takes under a tenth of one; a full cover cache no longer slows every new thumbnail; an album wall reopened shows its covers without reading them again; and with the library unchanged, the covers are left alone, so a NAS can sleep.
- **Lighter on long queues, playback and the library:** with 100,000 tracks in the queue, an add, remove, reorder, shuffle or heart held the window for up to 282 ms and now takes at most 31, and a long queue of tracks on a NAS that is away no longer takes seconds for every command. A track opens once rather than three times as it starts, on most tracks about 29 ms instead of 44, and steady playback no longer wakes the window with every position report. The loudness analysis goes straight from album to album, ten times faster for short albums, and rests while nothing changes, where it read about 1.4 GB every 30 seconds; with the two new indexes a first scan of 10,000 albums takes about a quarter less time.

## 0.4.1

Upgrading from 0.4.0 changes nothing in the library or the settings.

Changed since 0.4.0:

- **A double-click on a folder no longer closes CamelPlayer:** on the Folders page, a double-click on a folder further down a scrolled list opened the folder with its first click, and the second click, landing as the list was replaced, named no row; CamelPlayer read it anyway and closed, in every version since 0.1.0. A click that names no row is now ignored, in the folder, album, artist, track and playlist lists alike.

## 0.4.0

Upgrading from 0.3.0: the library gains a table for waveforms (library schema 21), and a copy of the library as it was is kept beside it as `library.db.v20.bak`. 0.3.0 refuses the newer library, so to go back to it, close CamelPlayer and, in `%LOCALAPPDATA%\CamelPlayer`, replace `library.db` with that copy. The settings keep their schema.

Background library work now goes at the Low scan speed, for libraries that were scanned before too: set Settings › Library › Scan speed to High for the speed of 0.3.0. Waveforms for the tracks you have are made in the background between 01:00 and 05:00, or at once when a track plays; ReplayGain analysis's own speed setting is gone.

As with every new version, the first complete library scan reads every MP3, and every file an earlier version could not read, once more.

Changed since 0.3.0:

- **A file read slower than it plays waits instead of breaking up:** a file on a network share that plays at 1 MB/s or more, such as DSD256 at 2.8 MB/s over Wi-Fi, is read for a moment before it plays. If it reads slower than it plays, playback waits, with a yellow "Buffering, about N s" bar above the player bar, until the rest will arrive in time, then plays without a break, buffering up to 1 GB in memory; should reading fall behind later, it pauses to buffer again rather than play in pieces. A network player or AirPlay receiver takes the audio over the same network, so for one of those the file is read at less than its full speed while it plays, the wait is longer, and the next track is read when the current one ends. Pause stops the wait.
- **Waveform:** the playback bar's position slider shows the playing track's waveform, as in Roon: the played part in the accent colour, each track scaled to its loudest, a click or drag seeking and the pointer showing the time there. An audio analysis makes it: at once for the playing track and the next; for the rest of the library in the background after the scan, in a window set in Settings › Library (01:00 to 05:00 by default, or any time), at the scan speed; and with ReplayGain on, in the loudness analysis's own pass, so no track is decoded twice. DSD goes through playback's DSD-to-PCM converter. Waveforms are kept in the library and made again when a file changes; Settings turns them off.
- **Scanning by hand:** **Scan now** in Settings › Library scans every library folder, and **Scan this folder** in a folder's right-click menu on the Folders page and in the folder tree scans that folder and everything below it, for a change the library missed, such as a tag edited on a NAS. Both look only for what changed, by size and modification time, run at High, are unavailable while a scan runs, and say so when the folder is offline.
- **Scan speed:** Settings › Library sets how much the library's background work takes (scanning, covers, fingerprints and ReplayGain analysis): Low, the default for everyone, uses one worker of each kind, Medium half of High, High as many as each can use. Adding a folder or rebuilding the library runs at High with the work following it; playback still comes first at every speed, and a change reaches running work at once. ReplayGain analysis's own Throttled and Fast setting is gone, folded into the scan speed.
- **File details:** "File details" in every track's right-click menu, and Alt+Enter on a selected row, opens a window beside the main one: a section for each tag format the file carries (ID3v2 with its version, ID3v1, APEv2, Vorbis comment, MP4, RIFF INFO, DIIN), every text tag by name and key with all its values, a mark with the library's value where the library shows a field otherwise, and the technical data with the ReplayGain tags and the library's analysis; pictures, lyrics and binary tags are left out and nothing is written. Every name and value is selectable and copies, and Open folder shows the file in File Explorer. A file that cannot be read shows why and what the library keeps.
- **Lyrics:** the player bar's cover opens the lyrics over the window, on the cover blurred: embedded (Vorbis, ID3 USLT and SYLT, MP4) or from a `.lrc` beside the file, synced over unsynced; synced lines follow what is heard, a translation under the same stamp lit with its line, a click seeks there, and scrolling by hand pauses the following for 3 seconds. The album name, no longer the cover, opens the playing album.
- **Start with Windows:** Settings › Interface can have Windows start CamelPlayer at sign-in, in the notification area and paused; the entry follows a moved folder, and one turned off in Windows' startup settings is shown as off and left so.
- **AirPlay to several receivers at once:** while a receiver plays, the output menu checks others into the group, in step and while it plays; the volume panel moves the group in proportion with a slider for each receiver; a receiver taken by another source or gone leaves with a notice while the others play on; the group comes back with any of its receivers and after a restart. A single receiver can play Stereo, Left or Right from its gear in Settings › Audio outputs, so two single HomePods make a stereo pair.
- **The output menu takes a mouse click every time:** a click on an output could leave it drawn pressed without choosing it, for the rest of the session, while the keyboard still chose; the menu is now built anew each time it opens and a click chooses on the press.
- **Go to playing in a folder tree with many folders open:** the button and Ctrl+L read every open folder again and showed the track before the folders above it had opened, which then pushed it out of view; the tree now opens only the closed folders on the way and shows the track once they are open.

## 0.3.0

Upgrading from 0.2.3: the first start gives each backend's settings to the device it had selected and enables the device in use (settings schema 4). 0.2.3 refuses the newer settings file, so to go back to it, close CamelPlayer, delete `settings.json` in `%LOCALAPPDATA%\CamelPlayer`, and choose your output again.

As with every new version, the first complete library scan reads every MP3, and every file an earlier version could not read, once more; on an 86,000-file library on a NAS that took about 7 minutes.

Changed since 0.2.3:

- **An output menu in the player bar:** it lists the outputs you enabled, marks those not connected and switches between them. A playing track goes on from the audible position with the queue unchanged, and a paused track stays paused. This replaces the output backend and device lists in Settings.
- **Settings › Audio outputs** lists every device found by backend, each with a switch for the menu and a name of your choice, and "Windows default device (WASAPI)" as an entry of its own. A new installation selects that entry; an upgrade keeps the device in use.
- **Network players are found:** UPnP AV and OpenHome players on your network are listed in Settings › Audio outputs, each kept by its identity, so one with several addresses appears once and one that gets a new address is still the same player. Turning the first one on explains the firewall rule network players need, for this program on private networks only, and Settings says so if the rule is missing.
- **Playing to network players:** choose one in the output menu and CamelPlayer streams to it, one URL per track, as WAV, L16 or L24 at the source's format unless DSP or a permitted conversion changes it, and raw DSD as DSF to a player that declares it. Tracks of the same format follow each other without a gap through the player's next-track function or its OpenHome playlist. The player shows the title, artists, album, length and cover. A seek, a DSP change or another track is heard about a second later, and the position shown is what the player has played. The player's own pause, play, seek, next and previous are followed; another source taking it over stops CamelPlayer with that reason, and a player that disappears pauses as not connected. The signal path says bit-perfect to the renderer.
- **A network player another source takes over is left alone:** CamelPlayer stops and sends the player nothing more, no stop, pause, volume or track, until you play to it again, so the other source keeps playing. A player that takes the stream but does not play, as a speaker in standby, is reported within about 5 seconds. These notices name the reason in the interface's language: in use by another source, not connected, or did not start playing, with a reminder to check that the player is on and not in standby.
- **Settings for each network player:** the highest PCM and DSD sample rates and bit depth to send, DSF or PCM for DSD, gapless playback on or off, silence after a format change, and a device release 60 seconds into a pause. A change reopens the stream only when the path differs.
- **A network player's own volume:** read when the player is chosen, followed from its remote and app, and written only when you move the 0–100 slider or mute. Only the choice between it and Fixed is kept, never a level, and software volume is no longer offered for these players.
- **AirPlay receivers are found:** Apple's own receivers on your network, HomePods, Apple TVs and Macs, are listed with the network players in Settings › Audio outputs, kept by their device ID, so one with a new address or name stays the same receiver, and a stereo pair appears once. A receiver CamelPlayer cannot use says why: it takes only encrypted audio, asks for a password, takes another format or refuses the connection, as a Mac does.
- **Playing to AirPlay receivers:** choose one in the output menu and CamelPlayer sends 44.1 kHz/16-bit stereo, to both speakers of a HomePod pair, unchanged for a CD-format source, with other formats going through the conversion rule. Tracks follow without a gap and crossfades work; a seek or a pause flushes the receiver and what follows is heard about 2 seconds later, which the position shown allows for. Its volume is set from the slider, and the last level is kept for each receiver, starting at about -20 dB. If another source takes the receiver, or it stops answering, playback pauses and says so.
- **A settings window for each output:** the gear on a row in Settings › Audio outputs opens that output's own settings, whether it is in use or not, without leaving the output playing.
- **The language changes at once:** choosing another language in Settings › Interface applies it straight away, without a restart, and playback goes on.
- **Clearer settings and status:** the settings links show the section you are in, the output menu names how each output is reached, the status badges are easier to hit and their text is centred, and the search box fits a small window.
- **DTS-CD is decoded by a Rust core, and FFmpeg is gone from the program:** the WAV decoders hand DTS-CD files to CamelPlayer's own decoder, which plays the 5.1 core; a DTS-ES file plays as 5.1 rather than 6.1, its rear center kept in the surrounds. FLAC, WAV and AIFF keep their other decoders, ALAC plays with Symphonia alone, and a saved FFmpeg choice falls back to the format's default.
- **Starts sooner, with a small library log:** the log SQLite keeps beside `library.db` grew at every start and stayed after a clean exit, past a gigabyte on a large library, and reading it held up the start. It now stays small and goes when CamelPlayer closes; the first start of this version folds in what is there. On a library of 86,000 files the window appears in about 0.6 s and the library is usable in about 2 s.
- **Scanning an unchanged library writes nothing:** every scan rewrote each file's and folder's row.
- **Closing on a busy machine:** with every core busy a scan could hold the program open for minutes after its window closed, and starting it again seemed to do nothing. It now saves the queue first and leaves within seconds.
- **A long queue stays quiet while playing:** with more than 2,000 entries in the queue, saving the queue every 5 seconds made CamelPlayer read through the library to check the queue's files, about 26 MB each time for a queue of 55,000. It now checks only when files or library folders change, and once a minute.
- **The first scan of a new version goes on where it stopped:** that scan reads every MP3 and every file an earlier version could not read again, and if CamelPlayer closed before it ended, the next start began it all over. It now reads only the files it had not reached.
- **The highest PCM and DSD rates for each output:** every output but WASAPI shared mode and AirPlay can be given a highest PCM sample rate and a highest DSD sample rate, for a DAC or digital converter that carries less than the device announces, such as one that plays DSD128 and up as silence. PCM above the highest rate is resampled to the top rate of its own family: under 192 kHz, 352.8 kHz becomes 176.4 kHz and 384 kHz becomes 192 kHz. DSD above the highest DSD rate is modulated again at that rate by CamelPlayer's own modulator, DSD256 to DSD64 for one, and stays DSD with DSP bypassed; the signal path shows the step as processed. DoP follows the highest PCM rate, so under 192 kHz DSD128 plays by DoP as DSD64. Choosing a limit is the permission to convert above it. Converting DSD to PCM is also about twice as fast.
- **What is playing is marked everywhere:** the album wall, the album lists of search and artist pages, the Folders page and the folder tree mark the playing album or folder with the playing or paused icon and the accent colour, every folder on the way down to the track included, and follow a change of track, a pause and a stop at once. **Go to playing** at the top of the library, or Ctrl+L, scrolls to it on the page you are on, opening the folders on the way, and selects the track; elsewhere it opens the track's album.
- **Playing a folder plays on:** with Settings › Playback › When playing from a folder set to go on to the end of its library folder, playing a whole folder, by a double click or Enter in the tree, the folder's Play button or Play now in its menu, also goes on to the folders after it, as a track chosen in it already did. Play next and Add to queue still add that folder only.
- **Each output keeps its own settings:** every WASAPI endpoint, ASIO driver and Kernel Streaming pin has its own parameters and fixed or software volume, and a device chosen for the first time starts from the defaults. Following the Windows default uses the settings of whichever device is the default. Deleting a saved device clears its settings, name and place in the menu; found again, it starts from the defaults.

Fixed since 0.2.3:

- **A HomePod pair paired again lost its settings:** the Home app gives a stereo pair a new identity each time it pairs it, so the pair came back as a new receiver, turned off, beside the old one shown as not connected. It is now known by its two speakers and keeps its name, settings, volume and place in the output menu, and the old entry goes.
- **A FLAC with a large cover started slowly from a NAS:** the Symphonia decoder read the whole embedded picture, often 3 to 4.5 MB, before the first sound, which held a start back by up to 1.5 seconds over Wi-Fi and the preparation of the next track as long. It now leaves the pictures out, as the libsndfile decoder already did.
- **Exiting could crash CamelPlayer:** a timer of the Home page could tick after the window closed and end the program before it closed its library, which the next start then treated as an unclean exit. Exit now stops every timer of the window first.

Changed since 0.2.1:

- **MP3 plays with mpg123 alone:** Settings › Decoders no longer offers FFmpeg, Symphonia or dr_mp3 for MP3. Measured from a NAS against them, mpg123 starts and seeks as quickly as the quickest, and it alone measures an MP3's exact length while it plays and then seeks exactly.
- **An MP4 whose sound is MP3 is no longer listed:** mpg123 reads MP3 streams only, so the scan passes such a file over and playing one reports it as unsupported.
- **AAC plays with Symphonia alone and ADPCM with libsndfile alone,** so Settings › Decoders lists only FLAC, ALAC, WAV and AIFF. A setting that named another decoder for MP3, AAC or ADPCM now plays with the one left.
- **AAC and MP3 always decode to 24-bit PCM:** the 16-bit option is gone. A device that takes only 16-bit gets them reduced with dither when conversion is allowed, shown as processed.
- **Suggestions for a word in many titles come at once:** the artists among them are looked up in an index of artists alone. With 100,000 tracks that all hold the word, the suggestions took 77–120 ms and now take about 7 ms.
- **MP3s from a NAS start and seek at once:** mpg123 read the whole file before the first sound to learn its exact length, which took 5–9 s over Wi-Fi. Playback now starts after the first frames, in under a second from the same NAS; the length the library knows shows at once and becomes exact while the file plays. A seek before the whole file has been read goes at once to where the target is estimated to be, by the Xing table or the length, and seeks land exactly once the file has been read: from the NAS a seek to 90 % right after the start plays within about half a second.
- **Another track starts at once while one plays:** a change by hand to a file in the format the device already plays keeps the device running instead of closing and reopening it, which cost the Chord DAVE's ASIO driver about half a second each time. Choosing a track from a NAS no longer asks the NAS about every track queued with it, nor how the chosen file is spelled, which the scan already stored: while the playing MP3 was read from the NAS, each question waited behind it, and a change took 1.4–6.7 s. On the same NAS a change now takes well under a second.
- **Symphonia 0.6.1,** the decoder for AAC and the default for ALAC, replaces 0.5.5.
- **dr_flac 0.13.4 and dr_wav 0.14.6** replace 0.13.3 and 0.14.5, with fixes for malformed FLAC metadata and block sizes, 32-bit FLAC, and AIFF sample rates.

Fixed since 0.2.1 (files an earlier version refused are read again once by the first scan after the update, so those below appear by themselves):

- **MP3 files whose audio does not follow the tag at once** were refused: a second ID3 tag, padding or other bytes between the tags and the first frame. The first frame is now found past them.
- **M4A files with a one-byte genre** were refused by Symphonia, the AAC decoder and the default for ALAC, because it reads the file's tags itself and gave up on that one. Symphonia now skips the tags, which CamelPlayer reads with TagLib anyway.
- **MP4 videos:** Symphonia took the picture track for the sound and refused the file. The first track it can decode now plays, so the sound of a music video or concert video plays like a track.
- **MP3s with a VBRI header** (written by Fraunhofer encoders) started with 26 ms of silence from mpg123, which decoded the VBRI frame as sound; they now start with their first audio frame.
- **An MP3 whose last frame is cut short,** such as by an ID3v1 tag written over the end of the file, ended in an error with mpg123 and skipped to the next track; it now ends normally.
- **MP3 lengths in the library could be wrong,** such as 1:29 for a 1:48 track with a VBRI header, which was estimated from the file's size, or seconds too long for a file without a Xing or Info header, whose estimate counted the cover art in its tags as sound. The first scan after the update estimates such lengths again, from the VBRI header or from the sound alone, and any MP3 length that differs from the decoded one is corrected once the track has played.
- **Symphonia refused a whole file** at an AAC frame it could not decode. Such a frame now plays as silence of its length.
- **macOS `._` files** (AppleDouble files with Finder data, left beside the music on a NAS) counted as audio files that could not be read; the scan now passes them over.

New features since 0.0.1:

- **More formats:** ALAC, WAV, AIFF, AAC-LC and MP3 join FLAC, each with its own decoder choice. AAC and MP3 decode to 24-bit (or 16-bit) PCM with encoder delay and padding trimmed for exact length and seeking. Files are recognized by their content, not their extension.
